地基 · 条件

什么是「条件」

生成不会凭空来——你给模型的每一样"要求"，都叫条件（condition）：
一句话→文生视频FL2VA
一张首帧图→图生视频FL2VA
首帧 + 尾帧→首尾帧过渡FL2VA
几张人物 / 物品参考图→参考驱动Ref2VA
一段要改的源视频→视频编辑Ref2VA
接上期：Flow Matching 把噪声一步步走成"一张画面"
条件决定的是——走到哪一张
模型怎么"吃"条件？各家做法完全不同
这正是 H3 最特别的地方
之前的做法

之前：两条流，一座桥

Wan2.2 的信息流
视频噪声 16 ⊕ mask 4 ⊕ 条件帧 VAE 16（首帧+补黑帧）
↓ 通道拼接成 36 · 进模型前焊死，条件从此没有独立身份
视频流（36 通道）主角 · 一直被加工
文本流T5 编码一次 · 之后不变
↓ 两条流始终分开 · 每层靠一座桥交互
① self-attention视频自己看自己
② cross-attention桥：视频拿自己当 Q，去文本里查 K/V
× 每一层都这样
桥每层都有，不稀疏
源码：WanAttentionBlock 里 self_attn、cross_attn 并列，× num_layers 层层如此
桥是单向的
context 进主干前编码一次，每一层原样复用——视频读文本，文本从头到尾不被更新
条件帧？通道拼接，不是 token
首帧过 VAE + 补黑帧 + mask，叠进输入通道：16 → 16+4+16=36——attention 够不着它，只能靠视频 token 二手传
好处：文本 K/V 可缓存，省算力
代价：条件进不了创作；每加一种条件 = 重新发明一次注入方式

一切成行

文本条件帧音频视频 四种原料，进模型前都变成同一种东西：「行」
原料加工得到每行维度
promptQwen3-VL 编码，取中间层512 行文本5120
首帧图视频 VAE → 切 2×2 小块1,008 行条件96

视频行占 95% —— 视频生成贵在这 每行随身三张身份证：模态 tag · 噪声水平 t · 时空坐标
放大 · 进门

维度对齐

self.proj_in = nn.Linear(96, 5376) # 视频行 self.audio_proj_in = nn.Linear(32, 5376) # 音频行 self.context_embedder = nn.Linear(5120, 5376) # 文本行 # 只有文本多走 2 层： text = self.token_refiner(text) # 把「猜下一个词」的表示掰成「指导画画」的
96→5376
32→5376
5120→5376
三个线性层，宽度对齐 · 此后再无模态专属权重
放大 · 主干

Attention · 好处在这一步兑现

① 看文本「prompt：一只橘猫，正在叫」= 内容对齐
② 看条件「参考图：这只猫长这样」= 长相对齐
③ 看音频「这一刻在叫 → 嘴张开」= 音画同步
④ 音频反过来看画面「嘴张了 → 叫声放这一刻」= 反向同步
结论：每一帧下笔前，内容、长相、声音一次对齐 —— 全看原文，零专门模块
代价：39,230² ≈ 15 亿对分数 → attention 占算力 80%
放大 · 出口

出口 · 哪些行的输出被留下

50 层跑完，每行还是 5376 维。两个线性头对每一行都算一遍，然后按行的身份「各挑各的」：
文本 512
条件 1,008
音频 414
目标视频 37,296
✗ 丢弃文本只当条件，不当产出
✗ 必须手动扔⚠ 预测会照常返回——不扔，首帧被一起去噪，直接跑飞
✓ 音频头5376 → 32 = 音频速度
✓ 视频头5376 → 96 = 视频速度
速度 → 挪一小步 → 回去再问 ↺ × 8 步 两个 VAE 解码 → mp4 5 秒片 13 秒出（4×H100 实测）
总结

拼在一起，值不值

好处
① 加条件 = 改拼法，不改架构（两个 ckpt 结构相同就是证据）
② 三模态 50 层互看 → 音画同步原生
③ 形态就是 LLM → 基建全白吃
代价
① 序列长，attention O(L²)，占算力 80%
② 文本行、条件行每步重新过 50 层
（Wan 的文本算一次、步步复用；H3 的每行跟着全序列变，存不下来）
一句话：拿算力换灵活性
